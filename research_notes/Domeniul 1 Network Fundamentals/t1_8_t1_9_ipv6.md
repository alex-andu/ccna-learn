## Q1. Why IPv6 exists — exhaustion, NAT, history

### Takeaway
IPv4's 32-bit space ran out at IANA level on 3 Feb 2011 and at RIPE NCC (Europe, incl. Romania) in Nov 2019; NAT only postponed the problem. IPv6 (selected as "IPng" in 1995) gives 128-bit addresses, a simpler fixed header, and autoconfiguration; its current spec is RFC 8200 (STD 86, July 2017).

### Cited Findings
- "The IANA IPv4 free pool was exhausted today, 3 February 2011." — [RIPE NCC news](https://www.ripe.net/about-us/news/ipv4-exhaustion-ripe-ncc-update/)
- RIPE NCC: no more /22 prefixes on 2 Oct 2019; "In November 2019, we exhausted our remaining IPv4 pool" (25 Nov 2019). Since then LIRs can only join a waiting list for a single recovered /24. A 2012 policy (triggered by reaching the last /8) had already limited each LIR to one /22. — [RIPE NCC: What is IPv4 Run Out?](https://www.ripe.net/manage-ips-and-asns/ipv4/ipv4-run-out/)
- RFC 1752 "The Recommendation for the IP Next Generation Protocol" (Bradner & Mankin, **January 1995**): IPng Area Directors' recommendation, accepted by IESG, adopted a revised **SIPP** proposal with **128-bit addresses** as basis of IPng (= IPv6). Design goals: simplified header, hierarchical addressing for route aggregation, packet-level authentication/encryption, plug-and-play autoconfiguration, redesigned options, flow labeling. — [RFC 1752 info](https://www.rfc-editor.org/info/rfc1752)
- RFC 1883 (first IPv6 spec): **December 1995**, S. Deering (Xerox PARC) & R. Hinden (Ipsilon), Proposed Standard, obsoleted by RFC 2460. — [RFC 1883 info](https://www.rfc-editor.org/info/rfc1883/)
- RFC 8200: STD 86, July 2017, Deering & Hinden, "obsoletes RFC 2460"; later updated by RFC 9673. — [RFC 8200](https://www.rfc-editor.org/rfc/rfc8200)
- RFC 2460 date: December 1998 [verify — not fetched].
- Why "v6" and not "v5": version number 5 was used by the experimental Internet Stream Protocol (ST-II) [verify — background knowledge].

### Inferences
- Didactic framing: IPv4 = 2^32 ≈ 4.3 billion addresses; IPv6 = 2^128 ≈ 3.4×10^38. One /64 subnet alone holds 2^64 ≈ 1.8×10^19 interface IDs — more than the whole IPv4 Internet squared (2^64 = (2^32)^2). (Pure arithmetic.)
- NAT drawbacks to teach (standard networking knowledge, [verify] wording against Odom OCG): breaks end-to-end principle, complicates inbound connections/peer-to-peer/VoIP/IPsec, needs ALGs, CGNAT (100.64.0.0/10) adds state and logging burden at ISPs. IPv6 aims to restore global addressing for every device; firewalls (not NAT) provide security.
- Timeline for a beginner: 1995 IPng chosen (RFC 1752) → Dec 1995 RFC 1883 → 1998 RFC 2460 → 2011 IANA exhaustion → 2017 RFC 8200 Internet Standard → 2019 RIPE run-out.

## Q2. IPv6 header vs IPv4 header

### Takeaway
IPv6 basic header is a fixed 40 bytes with 8 fields; header checksum, IHL, fragmentation fields and options are gone (options moved to chained extension headers; fragmentation only by the source host; upper-layer checksums mandatory).

### Cited Findings
- RFC 8200 §3 fields: **Version** 4 bits (=6); **Traffic Class** 8 bits; **Flow Label** 20 bits; **Payload Length** 16 bits (bytes after the IPv6 header, *including* extension headers); **Next Header** 8 bits; **Hop Limit** 8 bits (decremented by each forwarding node); **Source** and **Destination** 128 bits each. — [RFC 8200](https://www.rfc-editor.org/rfc/rfc8200)
- Extension headers defined: Hop-by-Hop Options, Fragment, Destination Options, Routing (AH and ESP specified elsewhere). Recommended order: IPv6 → Hop-by-Hop → Destination Options → Routing → Fragment → AH → ESP → Destination Options → upper layer. — [RFC 8200](https://www.rfc-editor.org/rfc/rfc8200)
- "fragmentation in IPv6 is performed only by source nodes, not by routers along a packet's delivery path." — [RFC 8200](https://www.rfc-editor.org/rfc/rfc8200)
- "IPv6 requires that every link in the Internet have an MTU of 1280 octets or greater." — [RFC 8200](https://www.rfc-editor.org/rfc/rfc8200)
- UDP checksum mandatory in IPv6: "IPv6 receivers must discard UDP packets containing a zero checksum"; ICMPv6 checksum includes a pseudo-header (Next Header 58). — [RFC 8200](https://www.rfc-editor.org/rfc/rfc8200)

### Inferences
- Size check: 4+8+20+16+8+8 = 64 bits = 8 bytes of fields + 2×16 bytes addresses = **40 bytes**. IPv4 header is 20 bytes minimum, up to 60 with options (IHL max 15×4) [verify vs RFC 791].
- Mapping table for the lesson:
  | IPv4 | IPv6 | Note |
  |---|---|---|
  | Version | Version | 4 → 6 |
  | ToS / DSCP+ECN | Traffic Class | same role (QoS) |
  | — | Flow Label | new |
  | Total Length | Payload Length | IPv6 excludes the 40-byte base header |
  | Protocol | Next Header | same values (6 TCP, 17 UDP) plus ext. header types; 58 = ICMPv6 |
  | TTL | Hop Limit | renamed to what it really does |
  | Header Checksum | **removed** | L2 (FCS) and L4 checksums already cover errors; routers no longer recompute per hop |
  | IHL, Options | **removed** → extension headers | fixed size = faster hardware processing |
  | Identification, Flags, Fragment Offset | **removed** → Fragment ext. header (source only) | routers send ICMPv6 "Packet Too Big" instead (PMTUD) [verify RFC 8201] |
- Why it matters for beginners: "simpler for routers" — fixed length, no per-hop checksum, no router fragmentation.

### Gaps
- RFC 791 not fetched; IPv4 header sizes stated from background knowledge.

## Q3. Notation, abbreviation (RFC 4291 + RFC 5952), prefix notation

### Takeaway
128 bits = 8 hextets (groups of 16 bits = 4 hex digits) separated by colons. Rule 1: drop leading zeros in each hextet. Rule 2: replace ONE run of consecutive all-zero hextets with `::` (only once). RFC 5952 canonical form adds: lowercase, `::` must cover the longest run (first one on ties), and never `::` for a single 0 hextet. Implementations must *accept* any RFC 4291 form.

### Cited Findings
- RFC 4291 §2.2: preferred form x:x:x:x:x:x:x:x, each x = one to four hex digits (e.g. 2001:DB8:0:0:8:800:200C:417A); "::" stands for one or more groups of 16 zero bits; "The "::" can only appear once in an address"; e.g. 2001:DB8::8:800:200C:417A; mixed form x:x:x:x:x:x:d.d.d.d e.g. ::FFFF:129.144.52.38. — [RFC 4291](https://www.rfc-editor.org/rfc/rfc4291)
- RFC 5952 §4 (systems SHOULD generate; all MUST accept RFC 4291 forms):
  - 4.1 "Leading zeros MUST be suppressed": 2001:0db8::0001 → 2001:db8::1; a single 0000 field → 0.
  - 4.2.1 "::" "MUST be used to its maximum capability": 2001:db8:0:0:0:0:2:1 → 2001:db8::2:1; 2001:db8::0:1 not acceptable (2001:db8::1 is shorter).
  - 4.2.2 "MUST NOT be used to shorten just one 16-bit 0 field": 2001:db8:0:1:1:1:1:1 correct; 2001:db8::1:1:1:1:1 not.
  - 4.2.3 longest run MUST be shortened: 2001:0:0:1:0:0:0:1 → 2001:0:0:1::1; equal runs → first: 2001:db8:0:0:1:0:0:1 → 2001:db8::1:0:0:1.
  - 4.3 hex letters MUST be lowercase.
  - §5 mixed notation only for last 32 bits and when a well-known prefix (e.g. IPv4-mapped) identifies it: ::ffff:192.0.2.1.
  - §6 address + port: [2001:db8::1]:80 SHOULD be used; 2001:db8::1:80 NOT RECOMMENDED (ambiguous).
  — [RFC 5952](https://www.rfc-editor.org/rfc/rfc5952)

### Inferences (worked examples — computed by me, rules per sources above)
| # | Full form | Canonical (RFC 5952) | Teaching point |
|---|---|---|---|
| 1 | 2001:0db8:0000:0000:0000:ff00:0042:8329 | 2001:db8::ff00:42:8329 | both rules |
| 2 | 2001:0DB8:0000:0001:0000:0000:0000:0001 | 2001:db8:0:1::1 | longest run wins (3 zeros vs 1) |
| 3 | FE80:0000:0000:0000:0000:0000:0000:0001 | fe80::1 | |
| 4 | 0000:0000:0000:0000:0000:0000:0000:0000 | :: | unspecified |
| 5 | 0000:0000:0000:0000:0000:0000:0000:0001 | ::1 | loopback |
| 6 | 2001:0db8:0000:0000:0001:0000:0000:0001 | 2001:db8::1:0:0:1 | tie → first run |
| 7 | 2001:0db8:0000:0001:0001:0001:0001:0001 | 2001:db8:0:1:1:1:1:1 | single 0 → NOT `::` |
| 8 | 2001:0db8:aaaa:0000:0000:0000:0000:0000 | 2001:db8:aaaa:: | `::` at the end |
| 9 | FF02:0000:0000:0000:0000:0001:FF00:0001 | ff02::1:ff00:1 | solicited-node |
| 10 | 2001:0db8:0100:0000:0000:0000:0000:0010 | 2001:db8:100::10 | TRAP: only *leading* zeros drop — 0100 → 100 (never "1"), 0010 → 10 |
| 11 | 2001:0db8:0000:00a0:0000:0000:0000:0000 | 2001:db8:0:a0:: | trailing zeros in a hextet stay (a0 ≠ a) |
| 12 | 0000:0000:0000:0000:0000:ffff:c000:0201 | ::ffff:192.0.2.1 | IPv4-mapped mixed notation |
- Expansion drill (reverse): count present hextets, `::` fills the rest up to 8. 2001:db8:a::b:c → 5 present → `::` = 3 zero hextets → 2001:0db8:000a:0000:0000:0000:000b:000c. fe80::1 → 2 present → 6 zero hextets.
- Invalid examples: `2001::db8::1` (two `::` — ambiguous: can't know how many zeros each hides); `2001:db8:12345::1` (5 hex digits); `2001:db8:g::1` (g not hex); `2001:db8:0:0:0:0:0:0:1` (9 hextets).
- Exam note: Cisco IOS *displays* uppercase (e.g. 2001:DB8::1) while RFC 5952 recommends lowercase; both are the same address — case is irrelevant.
- Prefix notation: `address/prefix-length` (like CIDR); no dotted subnet mask exists in IPv6. 2001:db8:acad:1::1/64 → network 2001:db8:acad:1::/64, IID ::1.
- Hex refresher for beginners: 1 hex digit = 4 bits (nibble); 4 digits = 16 bits = hextet; 32 digits = 128 bits. Prefixes on nibble boundaries (/48, /52, /56, /60, /64) are easy to read.

## Q4. Allocation hierarchy and IPv6 subnetting

### Takeaway
Typical chain: IANA → RIR → ISP/LIR (/32 or larger) → end site (/48 business, /56 residential) → /64 per LAN. On a /48, the 16 bits between /48 and /64 are the **Subnet ID** → 65,536 /64 subnets. LANs must be /64 (SLAAC needs it); /127 is recommended for router-to-router point-to-point links.

### Cited Findings
- RIPE-690 (BCOP, 16 Oct 2017): "/48 for business customers and /56 for residential customers"; "Assigning prefixes longer than /56 is strongly discouraged"; customers should be able "to have as many subnets (/64s) as they need"; "It is not possible to assign less than a /64 to each LAN port/segment/subnet/VLAN"; persistent (static) prefixes recommended by default. — [RIPE-690 (mirror)](https://hermesnode2.duckdns.org/publications/docs/ripe-690/) (official: ripe.net/publications/docs/ripe-690 [verify URL])
- RIPE NCC default LIR allocation is /32 (up to /29 without extra justification) [verify — search snippets only; e.g. [dreamserver lease page mentions /29 pool](https://dreamserver.ro/lir-services/ipv6-lease/)].
- RFC 6164 (April 2011): "Routers MUST support the assignment of /127 prefixes on point-to-point inter-router links"; reasons: ping-pong forwarding loops on p2p links with prefixes shorter than /127, and neighbor-cache exhaustion attacks on /64 links ("assigning /127 subnets eliminates it completely"); "Routers MUST disable Subnet-Router anycast for the prefix when /127 prefixes are used." — [RFC 6164](https://www.rfc-editor.org/rfc/rfc6164)
- RFC 4862: prefix length + interface identifier length must equal 128 or the RA prefix option is ignored; IID length defined per link type (RFC 2464 for Ethernet = 64) — [RFC 4862](https://www.rfc-editor.org/rfc/rfc4862)
- 2000::/3 is "The only block IANA currently assigns from" — [IANA IPv6 Address Space](https://www.iana.org/assignments/ipv6-address-space/ipv6-address-space.xhtml)

### Inferences (worked example — my arithmetic)
- Site prefix 2001:db8:acad::/48 → hextets 1–3 = global routing prefix (48 bits), hextet 4 = Subnet ID (16 bits), hextets 5–8 = Interface ID (64 bits).
  - Subnets: 2^16 = 65,536 → 2001:db8:acad:0::/64, 2001:db8:acad:1::/64, …, 2001:db8:acad:9::/64, 2001:db8:acad:a::/64 (decimal 10!), …, 2001:db8:acad:ffff::/64.
  - Trap: subnet "10" in hex is 2001:db8:acad:10::/64 = decimal 16; decimal 10 is `:a:`.
  - Scheme idea: encode VLAN ID in subnet ID: VLAN 10 → 2001:db8:acad:10::/64 (readable, hex digits used as if decimal) — common practice [verify phrasing].
- /56 residential: 64−56 = 8 bits → 256 /64s (e.g. 2001:db8:acad:4500::/56 → :4500: to :45ff:). /48 contains 2^(56−48) = 256 /56s. /32 contains 65,536 /48s.
- Finding the subnet of an address: 2001:db8:acad:12:abcd::5/64 → subnet 2001:db8:acad:12::/64. Tricky NetAcad-style question: 2001:db8:acad::aaaa:1234/64 with /48 → expand: 2001:db8:acad:0000:0000:0000:aaaa:1234 → subnet ID = 0000 (the `::` hides the subnet ID!). (Question pattern from [NetAcad PT 12.9.2](https://contenthub.netacad.com/courses/itn-dl/_common/12.9.2-packet-tracer---configure-ipv6-addresses-on-network-devices---physical-mode.pdf).)
- Non-nibble prefix (/62 etc.) worked example for deep dive: 2001:db8:acad:4::/62 covers :4:, :5:, :6:, :7: (last 2 bits of hextet 4 vary).
- No "network/broadcast address lost" like IPv4: IPv6 has no broadcast; the all-zeros IID is the Subnet-Router anycast (RFC 4291).

- RIPE allocation policy document (ripe-8xx current) not fetched; /32 default is widely known but unverified here.

## Q5. Address types (1.9.a–c): unicast (GUA, ULA, LLA), special, multicast, anycast

### Takeaway
Three categories: unicast (one-to-one), anycast (one-to-nearest), multicast (one-to-many). **No broadcast** in IPv6 — multicast (FF02::1, solicited-node) replaces it. Every IPv6-enabled interface always has a link-local FE80::/10 address; GUA 2000::/3 is Internet-routable; ULA FC00::/7 (FD00::/8 in practice) is the private-like range; site-local FEC0::/10 is deprecated.

### Cited Findings
- RFC 4291 §2.4 type identification: Unspecified ::/128; Loopback ::1/128; Multicast FF00::/8; Link-Local unicast FE80::/10; Global Unicast = "Everything else". — [RFC 4291](https://www.rfc-editor.org/rfc/rfc4291)
- Site-local: "Site-Local addresses are now deprecated"; "new implementations must treat this prefix as Global Unicast." — [RFC 4291 §2.5.7](https://www.rfc-editor.org/rfc/rfc4291). IANA: fec0::/10 "Deprecated in September 2004. Formerly the site-local scoped prefix." (deprecation RFC 3879 [verify number]) — [IANA IPv6 Address Space](https://www.iana.org/assignments/ipv6-address-space/ipv6-address-space.xhtml)
- IANA top-level map: 2000::/3 Global Unicast; fc00::/7 Unique Local Unicast; fe80::/10 Link-Scoped Unicast; fec0::/10 reserved (ex site-local); ff00::/8 Multicast; most other blocks "Reserved by IETF"; ::/96 IPv4-compatible deprecated. — [IANA IPv6 Address Space](https://www.iana.org/assignments/ipv6-address-space/ipv6-address-space.xhtml)
- IANA Special-Purpose registry (selected): ::1/128 Loopback (not forwardable); ::/128 Unspecified; ::ffff:0:0/96 IPv4-mapped (RFC 4291); 64:ff9b::/96 NAT64 well-known prefix (RFC 6052); 2001::/32 Teredo; **2001:db8::/32 Documentation (RFC 3849)**; **3fff::/20 Documentation (RFC 9637, new)**; 2002::/16 6to4; fc00::/7 Unique-Local (RFC 4193; forwardable True, globally reachable False); fe80::/10 Link-Local (forwardable False). — [IANA Special-Purpose Registry](https://www.iana.org/assignments/iana-ipv6-special-registry/iana-ipv6-special-registry.xhtml)
- ULA (RFC 4193, Oct 2005): 7-bit prefix FC00::/7 + **L bit** ("Set to 1 if the prefix is locally assigned"; "Set to 0 may be defined in the future") + **40-bit Global ID** + **16-bit Subnet ID** + **64-bit Interface ID**. Global ID sample algorithm: 64-bit NTP time + system identifier (e.g. EUI-64) → SHA-1 → "least significant 40 bits". "not expected to be routable on the global Internet"; AAAA/PTR "not recommended to be installed in the global DNS". — [RFC 4193](https://www.rfc-editor.org/rfc/rfc4193)
- IPv4-mapped: 80 zero bits + 16 one bits (FFFF) + 32-bit IPv4 — [RFC 4291 §2.5.5.2](https://www.rfc-editor.org/rfc/rfc4291)
- Multicast (RFC 4291 §2.7): format FF + 4-bit flags (0,R,P,T) + 4-bit scope + 112-bit group ID; T=0 = permanently assigned (well-known). Scope: 1 interface-local, 2 link-local, 4 admin-local, 5 site-local, 8 organization-local, E global; 0 and F reserved. — [RFC 4291](https://www.rfc-editor.org/rfc/rfc4291)
- Well-known multicast (IANA): FF01::1 / FF01::2 all nodes/routers interface-local; **FF02::1 All Nodes**; **FF02::2 All Routers**; **FF02::5 OSPFIGP** (all OSPF routers); **FF02::6 OSPF DRs**; **FF02::9 RIP Routers** (RIPng); **FF02::A EIGRP Routers**; FF02::D All PIM Routers; FF02::16 All MLDv2-capable routers; FF02::FB mDNSv6; **FF02::1:2 All_DHCP_Relay_Agents_and_Servers**; FF02::1:3 LLMNR; **FF02:0:0:0:0:1:FF00::/104 Solicited-Node**; FF05::2 all routers site-local; FF05::1:3 All_DHCP_Servers. — [IANA IPv6 Multicast Registry](https://www.iana.org/assignments/ipv6-multicast-addresses/ipv6-multicast-addresses.xhtml)
- Solicited-node: FF02:0:0:0:0:1:FFXX:XXXX = prefix FF02::1:FF00:0/104 + low-order 24 bits of a unicast/anycast address; RFC example 4037::01:800:200E:8C6C → FF02::1:FF0E:8C6C. — [RFC 4291 §2.7.1](https://www.rfc-editor.org/rfc/rfc4291)
- Address Resolution NS is sent to the target's solicited-node multicast; RS to all-routers (FF02::2); unsolicited RA to all-nodes (FF02::1); ND messages use Hop Limit 255 (proves on-link origin). — [RFC 4861](https://www.rfc-editor.org/rfc/rfc4861)
- Anycast: Subnet-Router anycast = subnet prefix + all-zero IID; "Packets sent to the Subnet-Router anycast address will be delivered to one router on the subnet." — [RFC 4291 §2.6.1](https://www.rfc-editor.org/rfc/rfc4291). IOS syntax `ipv6 address ipv6-prefix/prefix-length anycast`, example `ipv6 address 2001:0DB8:1:1:FFFF:FFFF:FFFF:FFFE/64 anycast` — [Cisco IOS IPv6 Command Reference](https://www3-realm.cisco.com/en/US/docs/ios-xml/ios/ipv6/command/ipv6-i1.pdf)
- Required addresses (RFC 4291 §2.8): a host recognizes its link-local per interface, configured unicast/anycast, loopback, All-Nodes multicast, and solicited-node of each of its unicast/anycast addresses (+ other joined groups); a router additionally the Subnet-Router anycast of routed interfaces, other anycast, and All-Routers multicast. — [RFC 4291](https://www.rfc-editor.org/rfc/rfc4291)

### Inferences
- GUA structure (RFC 4291 general format [verify section 2.5.4]): Global Routing Prefix (n bits, assigned by ISP/RIR, typically 48) | Subnet ID (m bits, 16 for /48) | Interface ID (64 bits). 2000::/3 = first hextet 2000–3FFF (first 3 bits 001). Today real allocations start with 2 or 3 (e.g. 2a02:… RIPE region, 2001:…).
- Link-local: FE80::/10 is the *reserved range*, but in practice the address is always fe80::/64 + IID (bits 11–64 are zero per RFC 4862 "bits in between to zero" — [RFC 4862](https://www.rfc-editor.org/rfc/rfc4862)). So valid LLAs start fe80–febf, but real ones are fe80::… Uses: NDP, router's RA source, **default gateway learned by hosts** (hosts use router LLA as gateway — [NetAcad 8.2.4.8](https://ccna.ilkom.unsri.ac.id/1/course/module8/8.2.4.8/8.2.4.8.html)), routing protocol next-hops (OSPFv3, EIGRPv6), never forwarded off-link (IANA: forwardable False). Must be unique only on its own link → the same fe80::1 can be configured on every router interface (NetAcad PT 12.9.2 does exactly this).
- Zone index: since every interface has fe80::/64, a host needs `%interface` to know where to send (Windows `fe80::1%12`, Linux `fe80::1%eth0`) [verify RFC 4007 — not fetched].
- ULA in practice: FD + 40-bit random = /48, e.g. fd3a:91c4:7e02::/48 (made-up example). FC00::/8 (L=0) not defined → never used. Analogy: "RFC 1918 of IPv6", but not intended to be NATed; meant to coexist with GUA.
- Multicast scope worked decoding: FF02::1 → flags 0 (well-known), scope 2 (link-local). FF05::1:3 → site-local. FF0E::… → global. FF3x:: → P=1,T=1 = SSM range (FF3x::/32) [verify RFC 4607] — deep-dive only.
- Solicited-node worked examples (my computation):
  - 2001:db8:acad:1::1 → last 24 bits 00:0001 → ff02::1:ff00:1. Note fe80::1 gives the **same** group → IOS shows only one FF02::1:FF00:1.
  - 2001:db8:acad:1:211:22ff:fe33:4455 → last 24 bits 33:4455 → ff02::1:ff33:4455 (the EUI-64 LLA fe80::211:22ff:fe33:4455 maps to the same group).
  - 2001:db8::abcd:1234:5678 → last 24 bits 34:5678 → ff02::1:ff34:5678.
- Why solicited-node exists: ARP in IPv4 broadcasts to all hosts (every CPU interrupted). IPv6 NS goes to a multicast group that, statistically, only the target joins (2^24 groups); NICs filter by multicast MAC 33:33:xx:xx:xx:xx (last 32 bits of the IPv6 group, RFC 2464 [verify]) so other hosts drop it in hardware. ff02::1:ff33:4455 → MAC 33:33:ff:33:44:55.
- Anycast beginner model: same address on several devices; routing delivers to the "nearest" (by routing metric). Real examples: DNS root servers, 6to4 relay; syntactically indistinguishable from unicast (RFC 4291 — taken from unicast space). Cisco CCNA depth: concept + `anycast` keyword + Subnet-Router anycast.
- Broadcast replacement table: ARP → NS to solicited-node; DHCP DISCOVER broadcast → DHCPv6 SOLICIT to FF02::1:2; "everyone on link" → FF02::1.

## Q6. Modified EUI-64 (1.9.d), privacy, SLAAC vs DHCPv6, NDP/DAD overview

### Takeaway
Modified EUI-64 turns a 48-bit MAC into a 64-bit IID: split MAC in half, insert FFFE, invert the 7th bit (U/L bit, value 0x02) of the first byte. It's predictable/trackable, so modern hosts use RFC 7217 stable-random or RFC 8981 temporary IIDs; Cisco routers still use EUI-64 for their auto link-local. Hosts learn prefix + flags from RA (NDP): SLAAC (A=1), stateless DHCPv6 (O=1), stateful DHCPv6 (M=1). DAD checks uniqueness with NS from `::`.

### Cited Findings
- Modified EUI-64: "The only change is inverting the value of the universal/local bit"; for 48-bit MACs insert 0xFF and 0xFE in the middle; resulting IID has U/L bit = 1 (for a universal MAC). — [RFC 4291 App. A](https://www.rfc-editor.org/rfc/rfc4291)
- Example MAC 0017.a4d2.27fc → "0017.a4FF.FEd2.27fc" → "Final result: 0217.a4FF.FEd2.27fc"; real IOS output "IPv6 is enabled, link-local address is FE80::C600:2FF:FEF4:0" / "2001:DB8:3C4D:15:C600:2FF:FEF4:0, subnet is 2001:DB8:3C4D:15::/64". — [learncisco.net](https://www.learncisco.net/courses/cisco-ccna/part-8-internet-protocol-version-6/how-it-works-2.html)
- Serial interfaces (no MAC): IOS uses MAC of the first available Ethernet interface for the link-local IID; LLA only needs to be unique on its link; LLA is auto-added when a GUA is configured. — [NetAcad 8.2.4.8](https://ccna.ilkom.unsri.ac.id/1/course/module8/8.2.4.8/8.2.4.8.html)
- IOS `eui-64`: "If the value specified for the /prefix-length argument is greater than 64 bits, the prefix bits have precedence over the interface ID." — [Cisco IOS IPv6 Command Reference](https://www3-realm.cisco.com/en/US/docs/ios-xml/ios/ipv6/command/ipv6-i1.pdf)
- RFC 8981 (Feb 2021) "formally obsoletes" RFC 4941; TEMP_VALID_LIFETIME default **2 days** (RFC 4941: 7 days), TEMP_PREFERRED_LIFETIME default **1 day**, random DESYNC_FACTOR; problem: a stable IID "is embedded within the IPv6 address, it cannot be hidden" → activity correlation; algorithm extends RFC 7217. — [RFC 8981](https://www.rfc-editor.org/rfc/rfc8981)
- SLAAC (RFC 4862, Sep 2007, obsoletes 2462): host appends its IID to RA Prefix Information prefixes that have the **A (autonomous)** flag; prefix + IID must = 128 bits; link-local = FE80::0 + IID; DAD: NS with source `::`, target = tentative address, to its solicited-node group; DupAddrDetectTransmits default 1; states tentative → preferred → deprecated → invalid; autoconfiguration of global addresses is for hosts (routers only do LLA + DAD). — [RFC 4862](https://www.rfc-editor.org/rfc/rfc4862)
- NDP (RFC 4861, Sep 2007): ICMPv6 types **RS 133, RA 134, NS 135, NA 136, Redirect 137**. RA **M flag** "addresses are available via DHCPv6"; **O flag** "other configuration information is available via DHCPv6"; Router Lifetime in seconds (0 = not a default router; max 9000); Prefix option **L flag** (on-link) and **A flag** (autonomous / SLAAC). Hop Limit 255. — [RFC 4861](https://www.rfc-editor.org/rfc/rfc4861)
- DHCPv6 client→server multicast FF02::1:2 — [IANA multicast registry](https://www.iana.org/assignments/ipv6-multicast-addresses/ipv6-multicast-addresses.xhtml)

### Inferences (worked EUI-64 examples — my computation; U/L bit = 0x02 of byte 1)
| MAC | Split + FFFE | 1st byte binary → flipped | Modified EUI-64 IID | LLA |
|---|---|---|---|---|
| 00:11:22:33:44:55 | 0011:22**FF:FE**33:4455 | 0000 00**0**0 → 0000 00**1**0 = 02 | 0211:22ff:fe33:4455 | fe80::211:22ff:fe33:4455 |
| 00:17:A4:D2:27:FC | 0017:a4ff:fed2:27fc | 00 → 02 | 0217:a4ff:fed2:27fc | fe80::217:a4ff:fed2:27fc |
| AC:DE:48:00:11:22 | acde:48ff:fe00:1122 | 1010 11**0**0 → 1010 11**1**0 = AE | aede:48ff:fe00:1122 | fe80::aede:48ff:fe00:1122 |
| 70:B3:D5:12:34:56 | 70b3:d5ff:fe12:3456 | 0111 0000 → 0111 0010 = 72 | 72b3:d5ff:fe12:3456 | fe80::72b3:d5ff:fe12:3456 |
| 02:50:56:AB:CD:EF (locally administered) | 0250:56ff:feab:cdef | 0000 0010 → 0000 0000 = 00 | 0050:56ff:feab:cdef | fe80::50:56ff:feab:cdef |
| C4:00:02:F4:00:00 (from IOS output above) | c400:02ff:fef4:0000 | 1100 0100 → 1100 0110 = C6 | c600:2ff:fef4:0 | fe80::c600:2ff:fef4:0 ✓ matches learncisco output |
- Shortcut for the exam: the 2nd hex digit of the MAC changes by ±2: 0↔2, 1↔3, 4↔6, 5↔7, 8↔A, 9↔B, C↔E, D↔F. It's a **flip (XOR)**, not "always set to 1" — trap when the bit is already 1 (row 5).
- Trap: FFFE goes in the **middle** (after the OUI, 3rd byte), not at start/end; "FFFE" not "FFEE"/"FEFF".
- Reverse drill: IID 0211:22ff:fe33:4455 → remove ff:fe → 02 11 22 33 44 55 → flip → MAC 0011.2233.4455. Seeing "ff:fe" in hextets 6–7 position (xxff:fexx) signals EUI-64.
- Why flip? Meaning inverted so manually configured IIDs like ::1 (U/L=0) read as "local", and ease of typing — RFC 4291 rationale [verify exact wording App. A].
- RFC 7217 "stable privacy": IID = hash(prefix, interface, network ID, secret key) → stable within a network, changes between networks; not derived from MAC [verify — RFC 7217 not fetched directly]. Windows and modern macOS/iOS/Android use random IIDs by default [verify].
- Client OS view (Windows `ipconfig`) illustrative [verify format]:
  ```
  Ethernet adapter Ethernet:
     Connection-specific DNS Suffix  . :
     IPv6 Address. . . . . . . . . . . : 2001:db8:acad:1:5d1c:8f2a:41b0:9e7c
     Temporary IPv6 Address. . . . . . : 2001:db8:acad:1:a4e1:3b77:c20f:12d9
     Link-local IPv6 Address . . . . . : fe80::5d1c:8f2a:41b0:9e7c%12

     Default Gateway . . . . . . . . . : fe80::1%12
  ```
  Points: "%12" = zone/interface index; gateway is the router's link-local; "Temporary" = RFC 8981 address used for outbound connections. Linux: `ip -6 addr` (shows `scope global temporary dynamic`, `scope link`), macOS `ifconfig` [verify].
- Three host-config methods (CCNA overview):
  | Method | RA flags | Address from | DNS/other from | Server state |
  |---|---|---|---|---|
  | SLAAC only | A=1, M=0, O=0 | prefix (RA) + self-made IID | RA RDNSS option (RFC 8106) [verify] | none |
  | Stateless DHCPv6 (SLAAC + DHCPv6) | A=1, O=1 | SLAAC | DHCPv6 | none (server tracks no leases) |
  | Stateful DHCPv6 | M=1 (A often 0) | DHCPv6 server | DHCPv6 | server keeps bindings |
  Default gateway ALWAYS comes from RA (source LLA), never from DHCPv6 — important trap [verify: DHCPv6 has no default-router option].
- NDP replaces ARP (NS/NA), ICMP router discovery (RS/RA), ICMP Redirect (137). DAD flow: tentative address → NS from :: to ff02::1:ffXX:XXXX with target = tentative → if NA received, duplicate (address not used); else address becomes preferred.
- IOS commands for RA flags (for later DHCP topic): `ipv6 nd managed-config-flag`, `ipv6 nd other-config-flag`, `ipv6 nd prefix … no-autoconfig` [verify].

### Inferences
**Exam traps list**
1. `::` used twice → invalid. 2. Removing trailing zeros (0100 → 1) → wrong. 3. `::` for a single zero hextet — accepted by IOS but not canonical (RFC 5952); exam answers usually show the "most compressed" form. 4. FE80::/10 is the range (fe80–febf); LLAs actually use fe80::/64. 5. ULA = FC00::/7, used FD00::/8; FEC0::/10 site-local is deprecated (distractor). 6. 2000::/3 = 2000–3fff; 2001:db8::/32 is documentation (won't route on Internet). 7. EUI-64: insert FFFE in the middle, flip (not set) 7th bit; MAC 02… becomes 00…. 8. EUI-64 needs a /64; `ipv6 address 2001:db8:1:1::/64 eui-64` — you type the prefix, not a full address. 9. No broadcast in IPv6 — any answer with "IPv6 broadcast" is wrong; FF02::1 is all-nodes multicast. 10. FF02::1 vs FF02::2 (nodes vs routers); FF02::5/6 OSPF, FF02::9 RIPng, FF02::A EIGRP, FF02::1:2 DHCPv6. 11. Solicited-node uses LAST 24 bits (6 hex digits), prefix ff02::1:ff00:0/104. 12. Forgetting `ipv6 unicast-routing` → no RAs, hosts don't get SLAAC, no forwarding. 13. `show ipv6 route` has C /64 + L /128 per address; LLAs not shown. 14. Host default gateway = router's link-local. 15. `ipv6 address autoconfig` (router as SLAAC client) ≠ router sending RAs. 16. Anycast addresses look identical to unicast; configured with `anycast` keyword. 17. Hex subnet IDs: :10: ≠ decimal 10. 18. Loopback is ::1/128 (not ::127). 19. Unspecified :: used as source during DAD/DHCPv6. 20. Prefix-length > 64 with eui-64: prefix bits take precedence (Cisco ref). 21. Point-to-point /127 is valid (RFC 6164) — but CCNA usually uses /64 everywhere.
